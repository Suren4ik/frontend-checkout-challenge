# Оформление заказа

Решение тестового задания: каталог, серверная корзина, оформление с расчётом доставки, тестовая оплата картой или наличными при получении. Фронтенд лежит в `apps/web` (`@checkout/web`), бэкенд не менялся.

Стек: React 19, TypeScript, Vite, TanStack Query 5, React Router 8. Поля формы проверяются схемами из `@checkout/contracts`.

Условия задания: [docs/ASSIGNMENT.md](docs/ASSIGNMENT.md), [API](docs/INTEGRATION.md), [критерии](docs/EVALUATION.md).

## Запуск

Нужны Node.js 24 и npm 11.

```sh
npm ci
npm run dev       # API на http://127.0.0.1:4000
npm run dev:web   # во втором терминале, фронтенд на http://localhost:5174
```

Другие команды:

- `npm run build:web` — проверка типов и сборка в `apps/web/dist`;
- `npm run preview:web` — собранная версия на http://localhost:4174;
- `npm run test:web` — unit-тесты (Vitest).

Если API запущен на другом адресе, укажите его в `VITE_API_URL` (пример в `apps/web/.env.example`).

## Как устроено

### Запросы

`createApiClient` в `src/api/http.ts` собирает запрос, добавляет токен сессии, отправляет его с таймаутом, проверяет статус, пустой ответ и конверт `{ data, meta, links }` и отдаёт `data`. Ошибки любого вида приводятся к `ApiError` с полями `kind`, `status`, `code`, `message`, `fields` и `requestId`. На 401 клиент один раз обновляет гостевую сессию (`src/api/session.ts`) и повторяет запрос.

`src/api/checkoutApi.ts` описывает только особенности эндпоинтов. Заказ и попытка оплаты создаются через `sendIdempotent` из `src/api/commands.ts`: ключ хранится в `localStorage`, пока исход запроса неизвестен. Повтор с тем же телом, даже после перезагрузки или двойного нажатия, уходит с тем же ключом. После любого определённого ответа ключ удаляется, и следующая попытка получает новый.

Кэш и загрузку делает TanStack Query. Ключи и `queryOptions` лежат в `src/api/queries.ts`. В `src/app/queryClient.ts` одна таблица описывает, что перечитать после ошибок устаревших данных: при `CART_VERSION_CONFLICT` — корзину и варианты доставки, при `QUOTE_EXPIRED` — расчёт и корзину, при ошибках оплаты — заказ и попытки. Правило срабатывает для всех запросов и мутаций, компоненты его не повторяют. Тексты ошибок для пользователя собраны в `src/ui/describeError.ts`.

### Корзина

Количество в API абсолютное. Нажатие сразу меняет число на экране, а запрос уходит через `KeyedLatestQueue` (`src/lib/latestQueue.ts`). По одной позиции одновременно выполняется один PUT или DELETE, а значения, пришедшие во время запроса, схлопываются до последнего. Поэтому запросы не идут параллельно и не приходят в обратном порядке. Итоги и версию корзины считает сервер: после изменения корзина перечитывается, и только потом снимается локальное значение. Если товара не хватает, количество возвращается к серверному, а у позиции появляется ошибка.

### Оформление

Поля проверяются схемами `CustomerSchema` и `DeliverySchema` из контрактов, то есть теми же, что и на сервере. `fields` из ответа API сопоставляются с полями формы по той же таблице путей. Некорректная форма на сервер не уходит, фокус переходит на первое поле с ошибкой. Черновик формы хранится в `localStorage`, так что ни сетевые ошибки, ни перезагрузка не стирают введённое.

Расчёт — это `useQuery` с ключом из версии корзины и доставки. Когда меняются товары или доставка, ключ тоже меняется, и поздний ответ по прежним данным на экран не попадает. Адрес пересчитывается через 400 мс после последнего ввода. До `expiresAt` расчёт считается свежим, и повторного POST нет.

При отправке корзина и расчёт перечитываются. Если итог отличается от показанного, заказ не создаётся: на экране появляется новая сумма, и её нужно подтвердить. Двойное нажатие отсекается сразу, ещё до перерисовки кнопки.

### Оплата

Состояние страницы оплаты берётся с сервера: заказ и последняя попытка из `GET /api/orders/{id}/payments`.

- `processing`: статус опрашивается через `refetchInterval` с паузой из `Retry-After`. Опрос прекращается на итоговом статусе и при уходе со страницы, после чего перечитываются заказ и попытки.
- `pending`: созданная, но не запущенная попытка используется повторно, иначе сервер не даст создать новую.
- `failed` и `cancelled` показываются разными сообщениями. Новая оплата создаёт новую попытку с новым ключом.
- Страница успеха открывается только по статусу заказа: `paid / succeeded` для карты и `confirmed` для наличных.
- Если заказ остался неоплаченным, после перезагрузки или возврата в каталог он находится по списку заказов, и над страницей появляется ссылка на оплату.

## Разбор участка: количество в карточках каталога

Каталог показывает у каждого товара количество из корзины. Если искать позицию через `cart.items.find` внутри `products.map`, получится O(товаров × позиций) на каждый рендер.

Рендер каталога повторяется на каждое изменение корзины: нажатие «+» или «−», ответ PUT, перечитывание корзины, смену локального значения.

`indexCartItems` один раз проходит по позициям корзины и строит `Map productId → позиция`. Индекс мемоизирован по ссылке `query.data`, а TanStack Query сохраняет эту ссылку, если перечитанная корзина не изменилась. Поэтому повторный GET без изменений индекс не пересобирает. Дальше рендер проходит по товарам один раз, и для каждого берёт количество за O(1): сначала из локальных значений, потом из индекса.

В памяти одна `Map` на версию корзины, для пустой корзины используется общий пустой индекс. Карточка товара обёрнута в `memo` и получает примитивы, поэтому при изменении количества одного товара перерисовывается только его карточка. Локальные значения копируют `Map` только при реальном изменении, иначе подписчики не будятся.

Так же устроены пункты выдачи (индекс строится один раз на ответ `checkout/options`) и остатки на странице корзины. Шапка подписана на корзину через `select: cart => cart.quantity` и перерисовывается только при изменении числа товаров.

## Что проверено

Вручную в Chrome на ширине 1280 и 390:

- каталог загружается из API, товар без остатка добавить нельзя;
- быстрые нажатия «+» уходят по одному запросу, итог совпадает с `GET /api/cart`;
- перезагрузка на `/cart` восстанавливает сессию и корзину;
- пустая форма не отправляется, ошибки у полей, фокус на первом неверном поле;
- самовывоз бесплатный, курьер при сумме меньше 5 000 ₽ стоит 390 ₽ по расчёту API;
- заказ картой открывает страницу оплаты с тестовыми картами из API;
- карта с отказом: ожидание, затем «Банк отклонил оплату», заказ тот же, можно оплатить снова;
- «Отменить оплату» показывает отдельное сообщение;
- успешная карта с перезагрузкой во время обработки: опрос продолжился, страница успеха открылась по статусу заказа;
- по API у заказа три попытки с разными id (`failed`, `cancelled`, `succeeded`), дублей нет;
- наличные с курьером: без онлайн-оплаты, страница «Заказ оформлен, оплата при получении» с номером, товарами, адресом и суммой;
- на ширине 390 каталог, корзина и оформление без горизонтальной прокрутки.

`npm run test:web` покрывает HTTP-клиент (конверт, 204, поля ошибки, обновление сессии при 401, сетевой сбой), ключи идемпотентности, очередь изменений корзины, проверку формы и описание доставки.

## Ограничения

- У количества нет debounce: нажатие, пришедшее после ответа на предыдущее, отправляет отдельный PUT. Схлопываются только нажатия во время запроса.
- Если сессия заменилась после 401 (например, после `npm run data:reset`), прежние корзина и заказы недоступны: сервер выдаёт новую пустую корзину, кэш сбрасывается.
- Черновик формы хранится в `localStorage` без срока жизни и очищается после успешного заказа.
- Сквозных браузерных автотестов нет.
